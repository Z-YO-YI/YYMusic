## 为什么先补数据

主指令17.1要求首页展示Repository的“最近添加”，但v1只保存文件modifiedAt，listTracks按标题排序。
不能把修改时间、标题顺序或本次启动时间伪装为加入曲库时间，因此先完成独立的数据升级增量。
首页三端布局、聚合Controller和真实播放入口将在后续批次使用该合同；HTML示例曲目不入生产。

## 实现与数据兼容

- v2只新增nullable tracks.added_at_ms和复合索引tracks_by_added；原17表/约束/现有索引保持。
  v1快照未变，SHA256为`ac5e1081f89f20f79f06b08331f5f1f522db0bcf0cd6fd20e5b6ecd19290f653`。
- 新入库曲目由Repository UTC时钟赋值，metadata冲突更新不包含此字段；重复扫描/可用性更新/
  并发写入不会重置。迁移的旧行保留NULL，首次时间未知的曲目仍在普通曲库，但不列作最近新增。
- listRecentlyAdded按包含端点的时间范围筛选，时间倒序后按完整TrackRef稳定排序；复用1–200条
  PageRequest，limit+1推导hasMore，数据库分页而非UI下载整库。不可用曲目仍保留并带既有可用性标记。
- 使用生成的版本化Schema2迁移助手，添加列/索引/审计同一事务；不关闭外键、不删库，失败保留v1。
  新建数据库直接记录v2创建审计；v1升级保留原审计并仅加一条v2，重开不重复写。
- 提交v2快照及Drift生成的历史Schema/测试助手；CI增加这些生成物的差异检查。
  不改依赖、权限、系统工具链、Window/Audio平台代码或用户真实数据库。
