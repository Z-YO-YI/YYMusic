# Phase 7J3：原生序列替换事件隔离

## 问题与基线

基线6b074e6，Z-YO-YI/YYMusic，干净工作区fetch/ff-only pull后建立codex/sequence-event-isolation。前轮序列身份映射为有效进展，但只有索引事件时，同一播放器整批换源不能识别迟到事件属于哪批；直接接根会把旧索引映射成新曲目。因此本轮先按ADR134处理该前置缺口，未缩减最终根策略/无缝要求。

读取锁定just_audio0.10.6的setAudioSources、dispose、stop、_disposePlatform及平台事件通道源码；以本机一手源码和真实插件通道测试为证据，不将猜测或最新依赖行为套用到当前版本。

## 实现

- NativeBackend第二次及后续open/openSequence先撤销订阅generation、取消旧订阅，请求pause并dispose旧AudioPlayer，再创建新AudioPlayer。插件激活使用新的原生播放器ID/事件通道，旧索引不能被新序列解释。同一批次内索引变化仍使用原播放器，不破坏序列内连续播放的基础。
- 音量及速率从原播放器复制，在订阅新播放器前恢复，避免向应用投影默认值闪变；不复制playing，不调用自动play。保留原代理/请求头能力配置及先整批预检后替换的顺序。
- 流通知、流错误、play请求迟到失败均校验generation。关闭后及可观察准备失败后拒绝新load/play；关闭交错不创建新播放器，暂停失败不继续替换。现有引擎仍负责串行化，后端不建立第二命令队列。

## 测试发现与未解决限制

最初释放失败测试未抛错。检查源码确认：_disposePlatform先尝试disposePlayer，失败回退platform.dispose；stop将两者失败吞掉，dispose又调用stop。因此第二次同时注入主/回退失败仍不能使公开dispose可靠抛错。这是插件边界事实，不是本项目能通过一个catch解决的问题。

新增替换前pause，它在playing时等待原生暂停确认并传播可见失败；该失败会阻止替换。但成功pause/dispose不等于资源释放证明。测试明确保留“释放错误被吞，但旧播放器已请求暂停”的证据，不能将该测试误写成释放失败检测通过。设备资源/生命周期验证以及必要的后端修正仍是上线前要求。
